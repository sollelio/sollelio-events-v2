# 0003 — Supabase integration foundation

**Status:** Accepted (Increment 1, Step 2)
**Date:** 2026-11-13 (accepted 2026-11-14)

## Context

Technical Foundation v0.1 names PostgreSQL via Supabase as the backend
direction and leaves environment variables, the environment workflow,
migration tooling and Supabase provisioning open (§10.3, §10.6). Product
approved a simplified infrastructure strategy: a single remote Supabase
project, `events-v2` (ref `icgsujzpcafqnqjozslj`). It has no real customers yet
and will eventually serve production. There is no local Supabase stack and no
separate staging project.

This step connects the application to that project. It creates no schema,
policies, functions, migrations, authentication screens or product features.

## Decision

### Dependencies (pinned exactly)

| Package                 | Version | Kind | Why                                              |
| ----------------------- | ------- | ---- | ------------------------------------------------ |
| `@supabase/supabase-js` | 2.119.0 | prod | Supabase client                                  |
| `@supabase/ssr`         | 0.12.7  | prod | Cookie-based sessions for Next.js server/browser |
| `supabase` (CLI)        | 3.1.0   | dev  | Source-controlled migrations; local by default   |

`@supabase/supabase-js` 2.119 requires Node.js ≥ 22, so `engines.node` is
raised from `>=20.9.0` to `>=22.0.0`. This is a dependency floor. It does not
choose the hosting runtime (§10.6 stays open).

### Environment variables

| Variable                               | Exposure | Purpose                              |
| -------------------------------------- | -------- | ------------------------------------ |
| `NEXT_PUBLIC_SUPABASE_URL`             | public   | Project URL                          |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | public   | Publishable key (`sb_publishable_…`) |

- Real values live in `.env.local`, which Git ignores (`.env*` is ignored and
  only `.env.example` is tracked).
- No privileged key (`sb_secret_…`, `service_role`) is configured or used.
  When one is needed, it gets a name without the `NEXT_PUBLIC_` prefix and is
  read only from `server-only` modules.

### Project target and validation (`src/lib/supabase/env.ts`)

- The approved project ref is a constant in code. The URL must be exactly
  `https://icgsujzpcafqnqjozslj.supabase.co`, so a misconfigured environment
  cannot point the application at another project (for example, V1).
  Retargeting is a reviewed code change.
- This hardcoded target is a deliberate **initial safety restriction** while
  `events-v2` is the only project. Revisit it when additional environments
  (staging, preview, a separate production project) are introduced, for
  example by replacing the constant with an explicit allowlist of approved
  project refs.
- The key must start with `sb_publishable_`. That rejects secret keys and
  legacy JWT keys (anon and `service_role`), so a privileged key cannot be
  inlined into the browser bundle by mistake.
- Validation is lazy: it runs when a client is created, not at import or
  build time. Pages that do not use Supabase are unaffected. Anything that
  creates a client fails with a clear error naming the variable, never its
  value. In production, Next.js redacts server error messages sent to the
  browser.

### Client separation (`src/lib/supabase/`)

| Module      | Guard         | Use                                                                                         |
| ----------- | ------------- | ------------------------------------------------------------------------------------------- |
| `client.ts` | `client-only` | Client Components; `createBrowserClient` (one instance per tab)                             |
| `server.ts` | `server-only` | Server Components, Server Functions, Route Handlers; one client per request via `cookies()` |
| `env.ts`    | —             | Shared validation of the two public values; holds no secret                                 |

Both clients use the publishable key and the user's session cookies, so RLS
applies to every query. Importing `server.ts` from a Client Component, or
`client.ts` from server code, is a build error.

### Migration workflow (Supabase CLI)

- `supabase/config.toml` was generated by `supabase init` (CLI 3.1.0) and is
  kept as generated. It configures the **local** stack only. It is not a
  record of the remote project's settings.
- **`supabase config push` is not used.** Its generated auth defaults (for
  example, `auth.email.enable_confirmations = false`) would conflict with the
  approved email verification (§3.1). Remote settings are changed in the
  Dashboard until the auth configuration is decided (§10.2).
- Migrations are plain SQL files in `supabase/migrations/`, created with
  `supabase migration new <name>` and committed. Applied migrations are never
  edited; a change is a new migration.
- CLI 3 targets the local stack by default. Remote commands need an explicit
  `--remote`, and remote changes ask for confirmation (`--yes` only in a
  deliberate, non-interactive run).
- Apply sequence, run only when a reviewed step authorises it:
  `migration list --remote` → `db push --remote --dry-run` → `db push --remote`.
  The dry run lists exactly the files that would be applied.
- Link once per clone with
  `supabase link --project-ref icgsujzpcafqnqjozslj`. Linking needs a personal
  access token (`supabase login`) and the database password, entered locally
  and never committed. Link state lives in `supabase/.temp/`, which Git
  ignores.

## Verification (2026-11-14)

All checks were read-only and printed no credentials.

- `GET /auth/v1/settings` with the configured URL and publishable key returned
  HTTP 200; the same request with an invalid key returned HTTP 401.
- The server client (in a Route Handler) and the browser client (in a Client
  Component, run in headless Chrome) each queried a non-existent table and got
  HTTP 404 `PGRST205` ("table not found"), not 401. The API accepted the key
  through both clients.
- A missing key returns HTTP 500 with an empty body; the server log names the
  variable. Wrong-side imports of `server.ts` or `client.ts` fail the build.
- The remote Auth settings already have email sign-up enabled and
  auto-confirm off. They were read, not changed.

## Resolves (Technical Foundation §10)

- §10.3 Migration tooling and workflow: Supabase CLI and SQL migrations in
  `supabase/migrations/`.
- §10.6 Environment variables. Environment workflow: one remote project; no
  local stack and no staging for now.
- §10.6 Supabase project provisioning: done by Product (`events-v2`).

## Deliberately deferred

- `proxy.ts` session refresh (`supabase.auth.getClaims()`) and auth cookie
  cache headers. They arrive with authentication; without sign-in there is no
  session to refresh.
- Authentication provider configuration, RLS design and server-side
  authorization structure (§10.2).
- Generated database types (`supabase gen types`), once a schema exists.
- Any secret-key or admin client.
- Staging, preview or CI environments; CI migration checks; test runner.
- Whether a local stack (Docker) is ever used for `db diff` or tests.
- PWA, offline support and Android packaging.

## Consequences

- The application cannot talk to any Supabase project but `events-v2` without
  a code change, until the restriction is revisited for additional
  environments.
- Because the only project will become production, every remote migration is
  effectively a production change. The dry run and review gate matter from the
  first migration.
- Without the local stack, schema changes are written as SQL by hand rather
  than diffed with `supabase db diff`, which needs Docker.
